# Design-system component inventory

This is the inventory the design-system guard reads. Every top-level Android
`@Composable` in `core/ui` (excluding `@Preview`) and every exported React
component in the admin kit has one row keyed by its name and source file. The
reference for how those parts are chosen and combined is the
[design system reference](design-system-reference.md).

Source files and caller paths are written as code spans, not links, because a
link would invite a reader to treat a generated helper as a stable entry point.
Same-file overloads share one row, keyed by `(name, source file)`; the
`Declarations` cell records the overload count and each signature. A call to a
name in a file counts for every overload in that file.

## Rule for a new or deleted component

A screen may not define a visual primitive the library lacks. A new component
lands with at least one caller, its states listed in this inventory, and render
coverage in the same change (Android screenshot states; admin test). A component
is deleted in the same change that removes its last caller.

A kit-pending component is the one exception: it may land with no production
caller when its row names a follow-up R-item in the Adopter column. Status and
Adopter are their own fields, never entries in Callers. The guard fails a
kit-pending row with no R-item adopter, and fails a kit-pending component that
gains a production caller; a component with callers is no longer pending.
